# 研 Buddy 金融投研评测集（app/benchmark/）

验证产品四件事：**取数正确、可追溯、合规拦截、显式降级**。思路对标财搭子团队开源的
[Fans-Pilot/financial_rag_benchmark](https://github.com/caidazi/financial_rag_benchmark)，
规模与评价方式适配"研 Buddy"产品形态。

## 结构

```
benchmark/
├── intents.json   # 意图体系（5 类：数值型/内容型×2/拦截型/降级型）
├── cases.jsonl    # 20 条评测用例（数值型 8 / 内容型 5 / 拦截型 4 / 降级型 3）
├── runner.py      # 评测脚本（PEP 723，uv run 直接跑；打后端 HTTP API）
├── results.json   # 最近一次基线结果（由 runner 生成）
└── README.md
```

## 对标 Fans-Pilot 的设计与裁剪

| Fans-Pilot | 本评测集 | 裁剪原因 |
|---|---|---|
| 意图分类（intents.json） | 同款：5 个意图各含说明与示例 | 保留；意图按产品能力边界划分而非按数据源 |
| 数值型查询，答案=数值+单位，Accuracy | 同款：期望值+单位，容差 ±0.05，要求值与单位同行出现 | 保留；期望值全部抄自 `backend/fixtures/` 已验证数据，不编造 |
| 内容型查询，Rouge/相似度+模型指标 | 改为：结论关键词命中率 + 证据四要素齐全率 + 必引证据字段出现率 | 本产品产物是"带证据清单的研究报告"而非自由文本，Rouge 对结构化产物不敏感；四要素齐全率直接对应产品"可追溯"卖点 |
| 查询源于真实用户日志 | 用例围绕演示主线（寒武纪 2026 中报）手工构造 | 24h 冲刺无真实日志；优先覆盖产品的合规/降级差异化能力 |
| —（无） | 合规拦截型 + 异常降级型 + 通用防编造核验 | 产品红线（不预测涨跌/不推荐买卖）与铁律（数字必须回指工具信封）是核心评分点，必须进评测 |

通用防编造核验（所有产出报告的用例）：报告中的每个数字必须能回指本次工具信封
（信封 data 数值 ±0.05、元→亿元换算、或作为子串出现在信封 JSON 的 as_of/caliber/URL 中），
否则判 FAIL。这直接验证架构铁律"产物数字由后端从信封渲染"。

## 运行

```bash
# 前提：后端已启动（fixture 模式即可）
cd app/backend && ALLOW_FIXTURE_FALLBACK=true uv run uvicorn app.main:app --port 8000

cd app/benchmark
uv run runner.py                    # 全量 20 条 → results.json + 终端表格
uv run runner.py --case num-01      # 单条调试
uv run runner.py --base-url http://<host>:8000
```

runner 对每条用例走完整产品链路：建线程 → `/run`（SSE）→ interrupt 后 approve → `/run`
→ 取报告与事件流 → 按意图类型打分，并统计每条用例的工具调用数与端到端耗时。

### 基线 v1 解读

- **取数正确 + 防编造**：数值型 8/8，全部用例的通用防编造核验通过——报告中数字 100% 可回指工具信封。
- **合规拦截**：4/4，guard warning 触发且均未进入研究计划，端到端耗时 ≈0s（不进图，零工具调用零成本）。
- **显式降级**：3/3，不存在标的 999999.SH 触发 `missing_key` 错误信封，报告明示"数据不足"且无编造数值；步骤标 failed 但任务正常走完产出报告。
- **可追溯缺口（评测发现的真实问题）**：内容型用例四要素齐全率 0.75——`ifind_announcement`
  工具信封缺 `as_of`（公告日期在 data 内部字段，未提升到信封层）。

## 已知边界

- fixture 模式下测的是"回放链路 + 报告渲染 + 合规/降级逻辑"，真实数据源的字段映射正确性需有 Key 后复跑确认。
- 内容型评价未用模型指标（LLM-as-judge），有 LLM Key 后可加一层语义评分作对照。
- 用例集中于单一标的单一报告期（演示主线），后续可按 fixtures 扩充扩充覆盖面。
